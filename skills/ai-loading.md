# Skill：AI渐进式提示词加载与文件定位

## 核心目标
专为AI辅助开发设计，实现「先读目录索引，再精准定位文件」的渐进式加载策略，既节省上下文Token，又让AI明确修改边界，严格遵守Keel规范。

## 知识金字塔：Prompt → AGENTS.md → Rules → Skills
控制AI行为有四个层次，从单次到复用、从即时到沉淀：

| 层次 | 解决什么问题 | 生命周期 | 何时使用 |
|------|-------------|----------|----------|
| **Prompt** | 「这一次」做什么 | 单次对话 | 临时任务、快速验证 |
| **AGENTS.md** | 「在这个项目里」怎么做 | 工作区级，自动加载 | 项目导航、全局约束、验证命令 |
| **Rules** | 「这类代码」应该怎么写 | 工程规范，按文件范围生效 | 代码风格、技术栈约束、命名规范 |
| **Skills** | 「这类任务」应该怎么跑流程 | 流程型知识，按需触发 | 调试、TDD、Code Review、部署 |

**沉淀路径**：先用Prompt快速验证 → 模式稳定后写入AGENTS.md → 跨项目复用时封装为Rules/Skills。

## 上下文三层治理法则
给AI的信息不是「越多越好」，而是「越准越好」。按三层管理上下文：

| 层级 | 内容 | 加载方式 |
|------|------|----------|
| **常驻上下文 (Permanent)** | 项目地图、AGENTS.md、全局约束、安全规则 | 始终加载，是系统运行的基石 |
| **按需上下文 (On-Demand)** | 接口定义、组件文档、模块规格、Rules | 根据当前任务动态加载，任务结束即释放 |
| **任务级上下文 (Task-Specific)** | 本次报错日志、具体目标、临时约束 | 极强时效性，完成即丢弃，开启新任务时果断清掉 |

**核心原则**：
- 只引用当前任务直接相关的文件/片段，拒绝全量暴力注入（可减少80%+冗余Token）
- 完成一个阶段目标后果断开启新会话，防止旧意图污染
- 简单任务用轻量模型，复杂任务用强模型，拒绝「杀鸡用牛刀」

### Smart Zone 法则
实证研究（Horthy, 2026）表明，AI上下文利用率与输出质量有一个"甜蜜区"：

```
  质量 ↑
       │  ╭──────────────╮
       │ ╱   Smart Zone  ╲    前~40%利用率
       │╱                  ╲   聚焦、准确、推理清晰
       │                    ╲
       │                     ╲___ Dumb Zone (>60%)
       │ 信息                 \   幻觉、循环、格式错误
       │ 不足   (0-40%)       \  （信息不足时需通过SessionStart加载）
       └──────────────────────────→ 上下文利用率
```

**规则**：
- 常驻上下文（Tier 1）严格控制在总窗口的**10-15%**以内——AGENTS.md要精炼，不要写成百科全书
- 按需上下文（Tier 2）加完后总利用率保持在40%以下
- 当对话变长、接近40%利用率时，主动触发**PreCompact内存刷新**：把当前任务、关键决策、下一步写入 `.sdd/anchor-state.md`，然后建议用户开启新会话
- 新会话启动时通过PostCompact从anchor-state.md恢复上下文
- 不要因为"上下文还没用完"就往里塞东西——**精准比海量更重要**

详见 `hooks.md`（PreCompact/PostCompact机制）。

## AI四层渐进式加载流程（强制执行）
禁止一次性加载全仓库代码！必须按以下四层顺序渐进读取：

### 第一层：全局认知（必读）
**目标**：了解项目整体目标、技术栈、全局规则，不读取任何业务代码
**读取文件**：
1. 根目录 `PROJECT_SPEC.md` - 了解项目目标、技术栈、全局约束
2. 根目录 `DIR_META.md` - 了解整体目录结构、模块划分
3. 根目录 `ERROR.md`（前半部分/统计）- 了解近期高频问题
**禁止**：这一阶段禁止读取 `src/`、`frontend/src/`、`backend/src/` 下的任何业务代码

### 第二层：模块定位
**目标**：根据用户任务定位到对应模块，确认边界与可修改性
**执行步骤**：
1. 根据用户需求，从根DIR_META.md找到对应的模块目录
2. 读取该模块目录的 `MODULE_SPEC.md` - 了解模块职责、对外接口、约束
3. 读取该模块目录的 `DIR_META.md` - 了解模块内文件结构、每个文件的可修改性等级
4. 确认本次任务涉及哪些文件，哪些是【可修改】、哪些是【谨慎修改】、哪些是【禁止修改】
**注意**：遇到【禁止修改】的文件必须停止，告知用户需要走评审流程；遇到【谨慎修改】的文件必须提醒用户风险

### 第三层：精准读取
**目标**：只读取任务涉及的目标文件，不读无关内容
**执行规则**：
1. 只读取DIR_META.md中列出的与任务直接相关的文件
2. 大文件只读取相关片段（函数/类定义），不全文读取
3. 读取对应文件的测试文件，了解预期行为
4. 查阅ERROR.md中该模块相关的历史问题，避免重复踩坑
**禁止**：不要遍历读取整个目录下的所有文件

### 第四层：修改与同步更新
**目标**：完成代码修改，同步更新所有相关文档
**执行步骤**：
1. 严格按Keel规范编写/修改代码，遵守可修改性分级
2. 编写/更新对应单元测试
3. 检查是否需要同步更新文档：
   - 文件增删/职责变化 → 更新 `DIR_META.md`
   - 功能/接口变更 → 更新 `MODULE_SPEC.md` 和 `API_SPEC.md`
   - 发现新问题/坑点 → 更新 `ERROR.md`
   - 重要变更 → 更新 `CHANGELOG.md`
4. 给出符合Conventional Commits规范的提交信息，包含docs-scope
5. 说明修改内容、影响范围、验证方式

## 文件可修改性分级规则
AI必须严格遵守DIR_META.md中标注的可修改性等级：

| 等级 | 标识 | 含义 | AI处理规则 |
|------|------|------|------------|
| 【禁止修改】 | 【禁止修改】 | 架构核心、实体定义、基础配置、第三方封装 | 禁止修改！必须明确告知用户该文件禁止修改，如需修改需走正式评审流程 |
| 【谨慎修改】 | 【谨慎修改】 | 公共组件、工具函数、通用接口、核心逻辑 | 修改前必须：1. 提醒用户风险 2. 列出所有调用方 3. 说明影响范围 4. 确认用户同意后再修改 |
| 【可修改】 | 【可修改】 | 业务逻辑代码、页面组件、非核心配置 | 在规格范围内可直接修改，但仍需同步更新文档和测试 |

## DIR_META.md 读取优先级
AI每次开始任务前必须按以下优先级检查目录元数据：
1. 根目录 DIR_META.md（第一层加载）
2. 目标模块的 DIR_META.md（第二层加载）
3. 目标文件所在子目录的 DIR_META.md（如有，第三层加载）

> **注意**：DIR_META.md只要求到模块级目录，子目录不需要每级都建。只有当子目录的职责、约束、可修改性需要特别说明时，才在子目录额外放置DIR_META.md。

## 编码禁令（必须遵守）
1. ❌ 禁止不读规格直接写代码
2. ❌ 禁止一次性读取/加载整个仓库代码
3. ❌ 禁止修改标注为【禁止修改】的文件
4. ❌ 禁止修改【谨慎修改】文件前不提醒风险
5. ❌ 禁止改完代码不更新对应文档
6. ❌ 禁止输出半成品、无法运行的代码片段
7. ❌ 禁止提交信息不写docs-scope
8. ❌ 禁止违反PROJECT_SPEC.md中的全局约束（命名规范、安全规则等）
9. ❌ 禁止跳过单元测试
10. ❌ 禁止重复ERROR.md中已记录的错误

## Debug的本质：不是修代码，是在补Spec
调试不是在「发现bug」，而是在发现「哪些需求还没有被说清楚」：
- Token永远为0 → 核心逻辑写入时机没定义
- 数据不更新 → 多线程/异步下数据流转路径没定义
- UI无内容 → 空数据处理规则没定义
- 类型不匹配 → 状态边界没定义

**Debug原则**：没有证据就不要修复。先理解问题（读错误信息、稳定复现）→ 形成假设（基于证据）→ 验证假设（最小实验）→ 在源头修复+添加防御性验证。修复完bug后，必须把发现的规则补回到对应Spec中（MODULE_SPEC/DIR_META/ERROR.md），形成正向迭代闭环。

**修根因而不修症状**：
- 用户报告的是症状（"这个接口返回500"），不是根因
- 在修改一个函数之前，grep它的**所有调用方**，理解完整的调用链
- 在共享函数/公共层加一个guard，比在每个调用方各打一个补丁diff更小、更彻底
- 只修报错路径而不检查其他调用方，等于在留下第二个bug
- 端到端追踪真实数据流，找到真正的故障点再动手，不要在错误位置做最小修改

## 多轮交互：单轮单目标
- 拒绝「一轮聊完所有事」，追求单轮交互意图高度纯粹
- 多任务并行会导致AI优先级错乱、逻辑混乱、旧意图污染
- 任务按阶段拆分：需求与设计 → 核心逻辑编码 → 功能与边界测试 → 结果验收与复盘
- 每轮聚焦一个目标，完成后再进入下一轮

## AI输出标准
每次完成开发任务，AI必须输出：

### 1. 修改内容清单
- 修改了哪些文件，每个文件改了什么
- 新增了哪些文件
- 删除了哪些文件

### 2. 文档同步情况
- 更新了哪些文档（DIR_META/MODULE_SPEC/API_SPEC/ERROR/CHANGELOG）
- 每个文档更新了什么内容

### 3. 测试说明
- 新增/修改了哪些测试用例
- 如何验证本次修改（构建命令、测试命令）

### 4. 提交信息
符合Conventional Commits规范的完整提交信息，包含docs-scope：
```
feat(user): 新增手机号登录功能

- 支持手机号+验证码登录
- 新增验证码发送接口
- 登录失败次数限制

docs-scope: docs/api/user.md, backend/user/MODULE_SPEC.md, backend/user/DIR_META.md
```

### 5. 风险提示
- 本次修改有哪些风险点
- 需要重点测试哪些场景
- 哪些【谨慎修改】文件被改动了，影响范围是什么

## 特殊场景处理

### 场景1：项目是全新的，还没有Keel文档
- 先帮用户建立基础的Keel结构（PROJECT_SPEC.md、根DIR_META.md）
- 确认技术栈、架构、全局规范
- 再开始写业务代码
- 第一个模块写完必须补全MODULE_SPEC和DIR_META

### 场景2：现有项目没有Keel文档，要加功能
- 先花少量时间梳理现有结构，补一个简单的根DIR_META.md
- 梳理目标模块的结构，补模块DIR_META.md
- 明确哪些文件能改哪些不能改，再开始修改
- 新代码按Keel规范写，老代码逐步完善

### 场景3：用户需求不明确/没有规格
- 不直接写代码
- 先帮用户梳理需求，输出简单的规格说明
- 确认验收标准
- 用户确认规格后再开始开发
- 按Keel流程走，不能跳过规格阶段

### 场景4：需要修改【禁止修改】的文件
- 明确告知用户：「该文件在DIR_META.md中标记为【禁止修改】，修改需要走评审流程」
- 说明修改原因、影响范围
- 建议用户走正式评审流程
- 如用户坚持要改，让用户明确确认，并在提交信息中标注「BREAKING CHANGE: 修改了禁止修改的文件XXX，原因XXX」
