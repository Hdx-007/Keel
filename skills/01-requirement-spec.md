# Skill 01：需求准入与规格输出

## 阶段目标
将业务需求转化为可执行的、冻结的Keel规格文档，确保产研测运四方对齐，无歧义进入开发。

## 适用触发条件
- 新功能需求提出
- 现有功能重大变更
- 新项目启动

## 参与角色与职责
| 角色 | 核心产出 | 评审关注点 |
|------|----------|------------|
| 产品 | 需求背景、用户场景、功能清单、验收标准 | 用户价值、业务逻辑完整性 |
| 开发 | 技术方案、模块拆分、接口定义、工作量评估 | 技术可行性、架构合理性 |
| 测试 | 测试范围、测试用例初稿、风险点 | 可测性、边界场景覆盖 |
| 运维 | 部署要求、资源评估、可观测性要求、监控指标 | 部署可行性、运维成本 |

## 执行步骤

### Step 1：需求收集与分析
1. 产品输出PRD或需求文档，包含：
   - 需求背景与目标（解决什么问题、带来什么价值）
   - 用户场景与用户故事
   - 功能清单（按优先级排序）
   - 验收标准（可量化、可验证）
2. 开发、测试、运维独立阅读需求，记录疑问点。

### Step 2：技术方案设计
开发团队基于需求输出技术方案：
1. 确定技术栈（参考L0已有选型，新增选型需ADR记录）
2. 模块拆分与职责边界定义
3. 接口契约初稿（API路径、方法、核心字段）
4. 数据模型设计（表结构、实体关系）
5. 工作量评估（按MDU拆分）

### Step 3：测试方案设计
测试团队输出测试方案：
1. 测试范围界定（哪些测、哪些不测）
2. 核心测试场景与用例初稿
3. 测试环境与数据准备要求
4. 风险点识别与应对策略

### Step 4：运维方案设计
运维团队输出运维方案：
1. 部署架构与环境要求
2. 资源评估（CPU、内存、存储、带宽）
3. 可观测性要求（日志、监控、告警指标）
4. 发布策略与回滚预案

### Step 5：四方评审与规格冻结
1. 召开评审会议，四方共同评审所有输出物
2. 评审通过标准：
   - 无P0/P1级遗留疑问
   - 验收标准全部可验证
   - 接口契约无歧义
   - 工作量评估各方认可
3. 评审通过后，正式输出L0/L1级Keel文档并冻结
4. 冻结后任何变更必须走「规格变更流程」

## 输出物清单
- [ ] `PROJECT_SPEC.md`（如为新项目）或更新记录
- [ ] 对应模块的 `MODULE_SPEC.md`
- [ ] `API_SPEC.md`（接口契约）
- [ ] 验收标准文档
- [ ] 测试用例初稿
- [ ] 运维部署方案

## 质量门禁
| 检查项 | 通过标准 |
|--------|----------|
| 规格完整性 | L0/L1所有必填字段已填写 |
| 接口契约 | 所有接口定义了路径、方法、入参、出参、错误码 |
| 验收标准 | 每个功能点有至少1条可验证的验收标准 |
| 可测试性 | 核心功能有对应的测试场景 |
| 可部署性 | 运维方案明确了资源要求与发布步骤 |

## 常见问题与应对

### Q1：需求不明确怎么办？
- 不允许带着疑问进入开发。
- 产品必须在评审前补充明确，或标注为「待确认」并给出确认时间。
- 待确认项不得影响核心功能开发，否则阻塞准入。

### Q2：技术方案有争议怎么办？
- 由技术负责人拍板，不同意见记录到ADR中。
- 重大架构分歧必须做技术预研，用数据说话。

### Q3：工作量评估达不成一致怎么办？
- 拆分MDU到更小粒度，重新评估。
- 以开发评估为准，产品可调整范围或排期。

## 反模式（禁止行为）
- ❌ 口头需求直接进入开发
- ❌ 边开发边改需求、补文档
- ❌ 评审走过场，遗留大量疑问
- ❌ 接口契约只写大概，细节等联调再说
- ❌ 不考虑运维和测试，开发完再说
