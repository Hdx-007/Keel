# Skill：闭环交付 Loop 机制

## 核心目标
主干分支永远可发布，每个开发单元都是完整可验证的闭环，禁止半吊子代码遗留。

## 最小交付单元（MDU）定义
任何开发任务必须拆分为MDU，满足以下INVEST原则：

| 原则 | 含义 | 判断标准 |
|------|------|----------|
| I - Independent | 独立性 | 不依赖其他未完成的MDU，可独立开发、测试、发布 |
| N - Negotiable | 可协商 | 范围可协商，不是必须固定死的合同 |
| V - Valuable | 有价值 | 对用户有价值，不是为了拆分而拆分 |
| E - Estimable | 可估算 | 工作量可估算，一般1-3人天 |
| S - Small | 短小 | 一个人1-3天能完成，最大不超过1周 |
| T - Testable | 可测试 | 有明确的验收标准，可独立验证 |

### MDU反模式（禁止拆分方式）
- ❌ 「写用户模块后端接口」（太大，包含多个功能）
- ❌ 「前端页面搭框架」（没有完整功能，无法验证）
- ❌ 「数据库建表」（没有业务逻辑，无法独立交付价值）
- ❌ 「只写一半接口」（无法测试，无法使用）

### MDU正例
- ✅ 「用户手机号+密码登录（后端接口+单测）」（1-2天）
- ✅ 「登录页面+表单验证+对接登录接口（前端）」（1-2天）
- ✅ 「用户信息查询接口（后端+单测）」（0.5-1天）
- ✅ 「个人中心页面展示用户信息（前端）」（1天）

## 迭代闭环门禁（10关缺一不可）
每个MDU从开发到合入必须走完以下完整流程，任何一环不通过都必须停在当前环节修复，不得流入下一阶段：

```
1. 规格确认 → 2. 代码开发 → 3. 单元测试 → 4. 文档同步 → 5. 本地构建通过
     ↓
6. 测试环境部署 → 7. 自动化测试 → 8. 人工验收 → 9. 合入主干 → 10. 归档沉淀
```

### 各阶段门禁标准

#### 1. 规格确认
- 对应的MODULE_SPEC/API_SPEC已写好并评审通过
- 验收标准明确
- 影响范围评估完成
- 相关方无异议

#### 2. 代码开发
- 代码按分层架构实现
- 符合代码规范
- 无debug代码、无注释掉的废代码
- 处理了异常场景和边界条件
- 没有硬编码的魔法值

#### 3. 单元测试
- 单测通过率≥90%，核心业务逻辑（涉及资金/数据一致性/鉴权/主流程）必须覆盖
- 包含正常场景、异常场景、边界值测试
- 测试代码清晰、可维护

#### 4. 文档同步
- DIR_META.md已更新（文件增删/职责变化时）
- MODULE_SPEC.md已更新（功能变更时）
- API_SPEC.md已更新（接口变更时）
- 代码注释完整（公共API、复杂逻辑）
- 提交信息包含docs-scope

#### 5. 本地构建通过
- 本地npm build/maven build/等构建命令无错误
- 代码检查（ESLint/Pylint等）无错误
- 本地运行无启动报错
- 无控制台ERROR日志

#### 6. 测试环境部署
- 代码部署到测试环境成功
- 服务可正常启动
- 依赖服务正常连接
- 数据库迁移脚本执行成功（如有）

#### 7. 自动化测试
- 自动化测试通过率≥90%，P0路径必须全过
- 前端组件测试/页面测试通过率≥90%
- 契约一致性校验通过
- 性能无明显下降（对比基线）

#### 8. 人工验收
- 产品按验收标准逐条验证通过
- 测试人员功能测试通过
- 交互符合设计稿
- 无明显体验问题

#### 9. 合入主干
- PR通过至少1人Code Review
- CI所有检查项通过
- 无冲突可干净合入
- 合入后自动部署测试环境验证主干健康

#### 10. 归档沉淀（Archive）
- 本次MDU的所有产出归档到 `changes/` 目录
- 更新CHANGELOG.md记录本次变更
- 发现的新坑点/规则沉淀到ERROR.md
- 必要时更新架构决策记录ADR
- 经验回写到Spec，让下一次做得更好

## MDU 归档机制（changes/ 目录）

每个MDU完成合入后，相关材料归档到项目根目录的 `changes/` 文件夹，形成可追溯的变更历史。借鉴OpenSpec的状态机思路，让每次变更都有完整的"从想法到落地"的记录。

> **适用说明**：小改动（单文件<50行、不改接口签名）可简化，不必创建changes目录；跨模块/大功能/5+人团队必须使用。

### 目录结构
```
project-root/
└── changes/
    └── YYYY-MM-DD-<short-slug>/     # 每个MDU一个目录
        ├── proposal.md               # 为什么做（需求背景、价值、目标）
        ├── specs/                    # 做什么（规格、验收标准、接口变更）
        │   └── <feature-name>.md
        ├── design.md                 # 怎么做（技术方案、架构决策）
        ├── tasks.md                  # 拆解任务清单（完成打勾）
        └── archive.md                # 归档记录（完成时间、合入commit、实际耗时、复盘）
```

### 各文件内容模板

**proposal.md**：
- 背景与动机：为什么要做这个变更？解决什么问题？
- 用户价值：对谁有价值？带来什么好处？
- 范围边界：做什么、不做什么
- 验收标准：怎么算完成

**design.md**：
- 技术方案概述
- 涉及的模块/文件
- 关键决策与取舍（为什么选A不选B）
- 迁移方案（如有数据变更）
- 风险与应对

**tasks.md**：
- [ ] 任务1（对应commit）
- [ ] 任务2
- [ ] ...

**archive.md**：
- 完成日期
- 合入commit hash
- 实际耗时
- 遇到的问题与解决方案
- 沉淀的经验（哪些需要补到Spec/ERROR.md）
- 后续follow-up（如有）

### 状态流转
```
propose（提案） → apply（执行中） → verify（验证中） → archive（已归档）
     ↓                ↓                ↓
   写proposal     完成tasks      测试验收通过
```

### 归档的价值
- **可追溯**：任何一个功能点，都能找到当初为什么做、怎么做的、遇到什么问题
- **可复盘**：archive.md记录了实际耗时和问题，为后续估算提供依据
- **可回滚**：每个变更的边界清晰，回滚时知道改了什么
- **知识沉淀**：经验不随聊天记录消失，而是变成项目持久资产
- **新人友好**：新人翻changes/目录就能理解项目演进历史

## 主干保护规则

### 分支保护设置
- `main`/`trunk`设为保护分支
- 禁止直接push，必须通过PR合入
- PR必须通过所有CI检查才能合入
- 至少1人审核通过才能合入
- 禁止force push到主干

### 主干健康保障
- 每次合入后自动部署测试环境
- 自动化测试全量跑一遍
- 部署失败立即回滚或修复
- 主干始终处于可发布状态
- 每天下班前主干必须是绿的
- **短分支+小PR+高频合入**：PR粒度尽量小（一个MDU一个PR），建议单个PR控制在500行以内，超过800行考虑拆分（但不要为拆而拆），降低review成本和冲突概率，AI生成代码犯错概率也大幅降低。避免一次性提交几百上千行的大PR。
- **增量改造优于推倒重来**：存量项目优先增量修改，不要让AI大段重写「屎山」，先让AI读懂边界再动手

### 版本标签
- 每次正式发布打tag：`vX.Y.Z`（语义化版本）
- tag对应代码必须是经过线上验证的
- 每个tag可随时构建、部署、回滚
- CHANGELOG.md记录每个版本的变更

## Code Review 五大重点
审核人Review代码时，重点关注以下五个维度：
1. **契约一致性**：接口字段、类型、错误码是否与API_SPEC一致
2. **关键路径正确性**：核心业务逻辑、边界条件、异常处理是否正确
3. **测试可验证性**：核心逻辑是否有单测覆盖，是否可独立验证
4. **可观测性**：关键链路是否有日志、TraceId、错误处理
5. **安全性**：鉴权、参数校验、SQL注入、XSS、敏感数据是否处理

## PR合入Checklist
PR创建时作者自查以下项目，审核人复审：
- [ ] 代码符合规范，无废代码、无debug代码
- [ ] 单测通过率≥90%，核心业务逻辑覆盖
- [ ] 相关文档已同步更新（DIR_META/MODULE_SPEC/API_SPEC）
- [ ] 本地构建和Lint/Typecheck通过
- [ ] 验收标准全部满足
- [ ] 提交信息规范，包含docs-scope
- [ ] 没有提交敏感配置、密钥等
- [ ] 数据库迁移脚本已验证（如有）
- [ ] 影响范围已评估，通知了相关方
- [ ] PR粒度合适（一个MDU一个PR，不混多个不相关功能）
- [ ] 已在changes/目录创建归档目录，proposal/design/tasks已就位（小改动可简化）
